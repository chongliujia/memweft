# qwen3-8b：任务相关性排序与学习反例

场景版本 `common-v2`，本机日期 2026-09-22。共 **145 次真实模型调用**：
训练 6 次、提案 1 次、验收对照 24 次、最终测试 114 次。温度为 0，seed=42，
每种配置重复两次；总 tokens 为 **30,768**，HTTP/推理累计约 **51.11 秒**。
这个耗时不包含 CLI 和数据库工作，也不是并发或冷启动性能指标。

## 实现

Rust `ContextOptions.query`、Python 同步/异步 `context(query=...)` 和 TypeScript
`context({query: ...})` 共用词项匹配排序。英文等文本按词项/数字切分，中文汉字按
相邻双字切分；统计不同匹配词项，key 匹配权重为 2，JSON value 匹配权重为 1。
排序发生在 `max_facts` 和预算裁剪之前，相同分数按 key 稳定排序。

`context.report.recall` 给出算法、查询词项、检查及匹配事实数、最终选中项的得分
和匹配词项；被裁掉的事实保留遗漏原因和得分。不传 query 时沿用 key 顺序。
检索范围仍遵守 tenant/user/agent 隔离，只处理有效事实。

当前实现是内存中的词项排序，会加载作用域内全部有效事实。它没有实现语义向量
检索、同义词理解或数据库查询加速。消息窗口和按 task_type 选择策略的行为保持原有语义。

## 检索改善与模型输出问题

三组使用同一个问题、目标记忆以及 40 条干扰记忆，保持 2048 估算 token 预算：

| 配置 | 候选上限 | 目标在最终上下文中的位置 | 估算 tokens | 有记忆组严格回答评分 |
|---|---:|---:|---:|---:|
| query 按当前问题排序 | 30 | 第 1 条 | 543 | 0/2 |
| query 排序并放宽上限 | 64 | 第 1 条 | 741 | 0/2 |
| 显式关闭 query，按 key 排序 | 30 | 被截掉 | 548 | 0/2 |

默认上限下，目标 `z_deployment_port` 的得分为 7，匹配 key 词项 `port`，
以及 value 中的 `当前`、`前部`、`部署`、`署端`、`端口`。目标不再因为 key 靠后
而被截掉。这证明了本次选择顺序修复的行为。

**检索改善没有直接变成端到端通过率提升。** 模型使用了正确端口，却把存储 key
用于输出，而题目要求字段为 `port`：

```json
{"z_deployment_port": 17443}
```

关闭 query 的对照仍返回 `{"port":null}`。由于字段名错误，query 两组的严格评分
仍然是 0/2；首轮出现的 `deployment_region`/`region` 字段混淆也继续存在。
原始题目和评分标准保持不变，未将“正确值但错误协议”改判为通过。

首轮放宽候选上限的对照回答为 2/2，本轮排序使目标移到首位后变为 0/2，表明模型的
输出字段也会受上下文排列影响。后续应增加显式输出契约，并独立测试其收益。

## 学习反例确实阻止了一次退化

训练反馈仍为原来的三类问题。新增的普通发票咨询、安全设置咨询、账号资料修改等
反例只放入验收与最终测试，提案器无法读取它们。每个分区使用不同问题表述。

验收结果：

- 基线通过 **8/12**，候选通过 **10/12**，平均增益约 **0.166667**。
- 原有支付与账号被盗问题得到改善。
- 在“账号没有异常，只想了解如何开启双重验证”的反例中，基线两次均输出
  `security/P2`，候选两次均错误输出 `account/P2`。
- Rust 检测到逐次退化，返回 **rejected**；`adoption_check.json` 确认策略列表仍为空、
  上下文与基线一致。未运行第二次提案去迎合验收集。

这次拦截的是错误分队，未观察到此反例中的优先级误升级。尽管整体均分提高，
候选对正常任务的损害仍能阻止采用。

最终保留测试中，原有工作流题目的有记忆及记忆加学习配置均为 **4/6**，新增反例
两种配置也均为 **4/6**。候选被拒绝后没有注入最终上下文；基线在本人新手机登录
验证题目上仍会把 `account/P2` 误判成 `security/P2`，这是后续需要改善的案例。

其他场景中，偏好、会话恢复、遗忘与隔离的有记忆配置继续全部通过；事实更新严格
评分仍为 2/4，原因与首轮相同。
