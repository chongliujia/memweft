本机运行日期：2026-09-22（Asia/Shanghai）。模型：`qwen3-8b`；接口：
`http://127.0.0.1:8002/v1`。场景版本 `common-v1`，temperature=0，seed=42，
关闭 thinking，每组重复两次，使用真实 Rust CLI 和独立 SQLite 数据库。

共完成 **109 次模型调用**，其中训练答案 6 次、策略生成 1 次、验收对照 12 次、
最终测试 90 次。服务器报告的全流程总 token 数为 **22,494**；模型 HTTP 调用
累计耗时约 **36.03 秒**，不包含场景准备、CLI 启动和数据库操作。

## 学习证据

模型只从训练反馈中生成以下策略（原文）：

> queue: billing, priority: P1 if the issue relates to payment processing or billing discrepancies; queue: security, priority: P0 if the issue involves account compromise or unauthorized access; queue: account, priority: P2 for general account-related issues like password reset.

验收集上，基线通过 2/6，候选通过 6/6，平均分提升 **0.666667**，没有逐次退化。
Rust `learning_submit` 返回 `accepted`。最终保留测试集上，基线通过 4/6，
采用后的策略通过 6/6；提升来自付款成功但权益未到账的工单优先级从 P2 改为 P1。
最终测试结束后执行真实 `learning_rollback`，确认策略被移除、上下文恢复为基线。

这说明在这组模拟业务规则中，反馈、提案、验收、采用、上下文应用和回退可以串通。
三个数据分区是同一组业务规则的不同表述，尚不能据此认定开放任务或多轮自改进有效。
候选把支付规则概括得比训练样例更宽，后续应加入“普通账单咨询”等反例检查误升级。

## 两个可定位的问题

### 1. 候选数量裁剪早于相关性选择

`recall-pressure` 保存 40 条以 `a_` 开头的干扰记忆，以及 key 为
`z_deployment_port` 的目标记忆。默认上下文按 key 排序后取 30 条，目标被遗漏。
实际 `context.report.omissions` 明确记录其原因为 `max_facts`。

此时估算上下文仅 548 tokens，低于 2048 预算；失败不是 token 预算耗尽。
将候选上限放宽到 64 后，41 条事实全部进入上下文，估算为 741 tokens，模型两次
均返回正确端口 17443。该对照支持优先开发按当前任务选择相关记忆，而不是单纯
增大默认上限。这里没有测量大规模数据库查询性能。

### 2. 存储字段名影响模型输出字段名

`update-region` 的上下文仅含最新区域 `eu-central-1`，旧值 `ap-southeast-1`
已经消失。题目要求输出 `region`，模型在两种有记忆配置下均返回：

```json
{"deployment_region": "eu-central-1"}
```

记忆更新正确，但输出字段名沿用了记忆 key，因此严格协议评分失败。
这应归类为输出结构遵循问题，不应计为“没有更新事实”。后续可独立测试显式 JSON
模板或约束输出，同时保留当前结果，避免修改评分标准后掩盖已观察到的失败。

## 下一轮开发建议

1. 给上下文构建增加当前任务线索及相关性选择，保留选择/遗漏解释；用压力场景验证。
2. 为应用输出定义明确的结构契约，分别报告信息正确性与协议符合度。
3. 扩充学习评测中的反例、边界案例与无关任务，检查策略过度概括和已有能力退化。
4. 在这一基线上再加入自动提取与纠错，分别评估写入错误、召回错误和推理错误。
