# 高频查询、写入与百万条并发验证

日期：2026-09-22。本轮基线是上一轮已经上线到代码中的 SQLite 倒排实现（索引 v1），不是最初的全量正文扫描。新增分数上界快速路径、索引 v2 及 SQL 语句复用；原有分词、权重、池优先级、有效期、CAS 和上下文预算保持不变。

## 实现与正确性边界

索引 v2 将现有 postings 主键调整为作用域、词项、权重倒序、item ID，使最大权重可通过索引定位取得，没有新增一份大型倒排索引。查询完整读取不超过 64 条的短列表，同时收集按 key 排序、已经通过资格检查的前缀。对其余长列表按池计算未见记录的分数上界；只有当前窗口足以胜过该上界，或同分时能证明 key 顺序领先，才提前结束。窗口包含一个额外候选以判断是否截断。

不能证明完整性的情况继续执行原来的全量 postings 聚合，包括分离的高频词列表、大候选窗口或过多词项/池组合。这不是近似召回，也不是完整的 WAND/Block-Max 实现。报告新增 `recall.ranking_plan`，取值为 `bounded_prefix`、`postings_aggregate`、`key_order` 或 `full_scan`；`sqlite_inverted_v1` 检索标识继续保留，不能将它当成数据库索引版本号。

每个连接复用事实写入、查询和触发器程序的已编译语句。没有缓存上下文结果，也没有减少提交次数或降低同步级别。候选、上界、正文和遮蔽诊断仍在同一个读事务中完成。

初次小样本测试发现候选评分 SQL 被优化成了作用域扫描；已改为从明确的候选 ID 列表驱动主键查找。下面均使用修正后的同一个 release 二进制，初次结果仅保留在 `bounded-recall-smoke/` 供审计。

## 百万条与保留的慢路径

主检索 scope 有 1,000,000 条私有事实，包含普遍出现的 archive、common，以及分布在不同记录中的 red/blue；末尾记录同时包含 red 和 blue。语料通过隔离旧库中的批量 SQL 建立，再用 v1 SDK 构建索引，这一步不计入查询计时，也不能用来声称 SDK 支持同速批量写入。before/after 都从这份 v1 库复制。全部 7 组输出一致。

## 百万条并发读写

8 个独立读进程，每个创建自己的 SDK 客户端；一个共享池写进程同时运行。所有进程经过启动屏障，断言读者执行区间确实重叠。每个读者交替执行 30 次低频、高频、混合词、value 高频查询，共 240 次；每次查询后再检查一次同 tenant/user 下 live 共享池的值与 revision，共 240 次快照检查。

主要查询读取私有百万条语料；写者更新独立的 live 共享池，约以至多 100 次/秒的节奏尝试 CAS 更新。该负载覆盖同库并发和跨 Agent 共享可见性，没有声称高频查询同时更新的同一批私有记录，也不是多写者吞吐极限测试。并发查询耗时不包含附加的 live 校验；吞吐按读者完整执行时长计算，包含该校验开销。

| 版本 | 查询 p50 / ms | 查询 p95 / ms | 完整循环查询数 / s | 上下文一致性检查 | live 快照检查 | 同期写入次数 |
|---|---:|---:|---:|---:|---:|---:|
| v1 | 1829.22 | 2559.33 | 5.28 | 240 | 240 | 3712 |
| v2 | 2.44 | 3.68 | 2165.66 | 240 | 240 | 6 |

v2 的这轮 240 次查询只持续约 0.11 秒，仅与 6 次写入重叠；这属于短突发测试，不能作为持续并发吞吐证明。两组运行时长不同，因此写入次数不同，不能将写入次数之比解释为吞吐提升。所有查询内容均与各自串行基线的 SHA-256 一致，live 值中的 generation、mirror 及报告 revision 一致，运行后 SQLite 完整性和外键检查通过。

### 持续 60 秒补充实验

为补齐短突发限制，`soak_bounded.py` 在存储压测结束后单独运行，旧/新库各复制百万条测试文件；8 个读者各自循环至少 60 秒，仍有一个共享池写者，查询组合和逐次校验相同。两组所有读者和写者执行区间均实际重叠，查询结果、live 修订快照及运行后完整性/外键检查全部通过。

| 版本 | 读者时长 / s | 查询及快照校验各自次数 | 查询 p95 / ms | 完整循环查询数 / s | 写入次数 | 写入 p95 / ms |
|---|---:|---:|---:|---:|---:|---:|
| v1 | 61.60 | 323 | 2440.19 | 5.24 | 4,962 | 2.65 |
| v2 | 60.00 | 209,550 | 2.95 | 3492.32 | 1,103 | 76.73 |

**读性能改善的同时，持续负载下的写入长尾明显恶化。** v2 写入 p50 为 45.50 ms、p95 为 76.73 ms，旧版分别为 0.59 和 2.65 ms；写者每次完成后仍额外等待 10 ms。闭环读者会在查询变快后发出更多请求，两个版本承受的实际读取速率不同，因此这些结果既不能证明同等到达速率下写入必然退化，也不能宣称读写性能全面改善。下一轮应增加相同到达速率和不同读写配比，测量排队、CPU、磁盘同步与 checkpoint，再定位原因。此处的查询组合不包含必须聚合的 `red blue` 慢路径；60 秒单轮实验仍不是长期稳定性或生产 SLO 验证。

## 迁移与磁盘成本

v1 升到 v2 在一个事务中复制并重排 postings、替换触发器并更新版本。迁移阻塞写入，并需要临时空间；失败时旧版本、表和触发器一起回滚。没有自动 VACUUM：旧页面作为空闲页留在文件中供复用。下表为各轮写入（百万条轮次还包括并发）结束后的文件和页面统计；已包含额外测试 user 的记录。迁移过程中还需要 WAL 空间，下表不是迁移磁盘峰值测量。

- Python 12 项通过、2 项外部 DSN 测试未配置而跳过；Node 6 项通过，TypeScript 构建通过；离线评估工具 37 项通过。异步 SDK 测试在本机完成，未把沙箱下未执行的子测试算作通过。
- 独立存储压测在查询基准之后运行：8 客户端 800 次 CAS 尝试，100 次成功、700 次预期冲突；160 次相同消息提交只保留 1 条。100 组 tenant/user × 2 Agents 无私有/会话泄漏，200 次只读修改被阻止。
