# 三种上下文策略的冻结工作流对照

这轮评测比较同一批明确记录，通过完整历史、当前状态摘要和 MemWeft 检索提供给模型时，
任务正确率与上下文成本有什么差异。题库包含 20 个新的合成工作流任务：项目交接、
故障排查、客服处理、需求变更、约束规划各 4 题。它不是客户任务或生产验收。

## 运行

安装 Python SDK 后，在仓库根目录运行：

```bash
python evals/run_workflow_comparison.py --check-memory --output data/evals/workflow-offline-new
python evals/run_workflow_comparison.py --prompt-key --output data/evals/workflow-live-new
```

第二条命令会产生费用：20 题 × 3 种策略，共 60 次 Kimi K2.6 调用；关闭思考，
每次最多 192 个输出 token，默认请求开始时间间隔至少 21 秒，完整运行约 21 分钟。
密钥只从隐藏终端输入或 `MOONSHOT_API_KEY` 读取；不保存密钥、不自动加载 `.env`。
使用大陆 API 地址，不自动切换服务商或端点。

默认最多 60 次调用、累计已报告 100,000 token 后停止后续请求，每份 `messages` 的
UTF-8 JSON 最多 16,000 字节。字节限制不包含模型名等 HTTP 请求体附加字段。
这组限制不是严格的人民币预算：累计 token 只能在完成调用后更新，最后一次可能越过阈值。
可用 `--max-calls`、`--token-limit`、`--max-request-bytes` 降低限制。
接口错误或计费 token 缺失立即停止，不自动重试；保留已经完成的结果。
输出目录必须是新目录，避免覆盖历史证据。

完整运行结束后，生成可复核的报告：

```bash
python evals/report_workflow_comparison.py --run data/evals/workflow-live-new \
  --json data/evals/workflow-report-new.json --markdown data/evals/workflow-report-new.md
```

报告器无需原生 SDK 或 API 密钥。它要求完整的 60 个唯一题目/模式配对，重算评分并核对
实际请求、冻结输入、用量、汇总及源码哈希；未完成的运行和被修改的不一致结果会被拒绝。
两份报告都必须使用新文件名。

## 对照口径

每题有 2–5 个主事实，加上固定 16 个无关档案事实。事实由评测明确写入，三组获得
相同源事件、作用域边界、当前问题、业务规则和输出字段要求。问题及期望答案不参与
摘要构建，期望答案只供本地评分，不发送给模型。

| 模式 | 传给模型的上下文 |
|---|---|
| `full_history` | 按时间排列的全部可见记录，保留同键更新的历史 |
| `current_state_summary` | 确定性维护每个键的最新值，不根据问题挑选事实 |
| `memweft` | 真实 Rust/Python SDK 关闭并重新打开数据库，按当前问题检索；最多 8 个事实、1,200 个估算 token |

摘要不是模型生成的，不产生摘要调用费用。遗忘对三组同样生效：完整历史会删除该键
已撤回的旧值，保留遗忘事件；另外两组不再提供该事实。其他作用域的数据对三组都不可见。
因此“完整历史”指遵守删除要求的历史，而不是把已经遗忘的内容重新发给模型。

三组共享请求字节上限和模型输出上限；实际输入 token 数可以不同，这正是成本比较对象。
MemWeft 的检索限额只约束自身上下文，不把完整历史或摘要截断到同一数量。每题轮换调用
顺序，减少固定顺序影响，但不能排除服务端缓存和负载波动。

## 冻结与证据

[题库](../evals/scenarios/workflow-comparison-v1.json) 的 SHA-256：

```text
1c97c7e387f4772d81dbc1282b3bd1401b246b4014635f92dae029d630a14d29
```

所有 60 份实际输入会在第一次付费请求前写入 `inputs.jsonl`。每个运行目录另保存题库、
模型与限额元数据、源码和原生扩展哈希、原始请求/响应、用量、逐项评分及 SQLite 数据库。
已有题目和答案不根据本轮模型输出调整。最终报告要求全部 60 次完成，并重新核对输入、
输出契约、评分与统计。没有自动修复答案或重试到通过。

每个题目、每种策略只测一次，模型使用服务商默认采样。因此结果用于发现问题和比较
这一份题库的成本，不能解释成稳定的成功概率。任务同时包含条件判断、数量和时间计算，
失败需要区分事实没有进入上下文与模型读到事实后推理出错。

报告的延迟为上下文构建加模型 HTTP 时间，不含数据写入、初始化和限速等待；它不是完整
记忆系统生命周期延迟。费用按服务商报告的输入/输出 token 估算，不计缓存折扣，不是账单。
本轮不测试自动抽取、策略学习、语义向量检索、长时间服务稳定性或真实业务收益。

## 2026-09-30 实测与下一步

[完整实测报告](../evals/reports/2026-09-30-workflow-comparison.md)保存了 60 次调用的复核结果：

| 模式 | 通过 | 输入 token | 估算费用 |
|---|---:|---:|---:|
| 完整历史 | 18/20 | 21,551 | ¥0.153501 |
| 确定性当前状态摘要 | 19/20 | 15,761 | ¥0.115865 |
| MemWeft 检索 | 16/20 | 8,937 | ¥0.071510 |

总估算费用 ¥0.340876。MemWeft 输入 token 比完整历史减少 58.53%，比摘要减少 43.30%；
本轮正确率也更低，不能把节省量解释为无损压缩或在质量相同时的优势。

MemWeft 的四个失败中，证书排查遗漏当前时间、退款遗漏单价/币种；两者都是与问题没有
直接词法匹配的关联事实。另两题的必要事实已经进入上下文，模型仍在取消需求和维护时间
窗口上违反业务规则。退款题还返回了契约不接受的 null，协议有效为 19/20。
完整历史在留存天数和维护结束时间两题失败，摘要在留存天数一题失败。

下一步优先验证两个方向：让应用声明业务需要的事实槽位或关联关系，召回后补齐缺失依赖；
对金额、时间和明确业务规则增加程序校验，校验失败时澄清或重新获取信息。之后使用新的
未见题目和重复观测验证，保留这批题作为回归测试，不根据它们改答案或宣称普遍提升。

首次实测在运行期间补记了评分依赖和 Python 包装层的源码快照；调用前记录的三项源码
哈希与补记内容一致，细节保留在报告。实测结束后，运行器已改为在首次调用前自动归档
这些文件，并原样保存题库字节。归档改进没有改变本轮请求、答案或评分。
