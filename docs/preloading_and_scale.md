# 预加载、分片与 RDMA：大规模记忆检索设计

日期：2026-09-22。本文是后续设计建议，不代表当前 SDK 已有预加载、分布式分片或 RDMA 接口。当前实现及实测见 [索引检索](indexed_retrieval.md) 与 [百万条验证](../evals/reports/2026-09-22-bounded-recall.md)。

用户已明确：**既要支持跨租户/Agent 的总量达到千万、上亿，也要支持单个大型记忆池达到这一规模。** 后续不能只用“小作用域分散总量”的测试代替超大单池测试。

## 数据多是否必然慢

总记录数和一次请求的工作量不是一回事。延迟取决于路由到多少作用域、访问多少索引项、缓存是否命中、评分/排序工作和并发排队。有效的索引与剪枝能避免线性扫描；复杂查询、宽范围查询或宽松的分数上界仍可能处理大量候选。

本项目目前的百万条热缓存实验中，能证明提前结束的高频查询约 2 ms；必须全量聚合的组合查询仍约 2.3 s。两者的数据总量相同。因此缓存和算法需要一起处理，不能仅根据“一亿条”推断延迟。

也要区分“全部租户合计一亿条”和“一个共享池一亿条、一次查询横跨整个池”。前者可先按作用域缩小范围，后者更依赖分块跳过、压缩、并行搜索和分片合并。这些是本项目的架构判断，尚无千万/亿级测量证明。

## 推荐先支持有预算的热点预热

Elasticsearch 主要依赖操作系统文件缓存，也支持打开索引时预加载指定的热点索引文件。官方同时提醒：加载过多文件，尤其索引超过可用内存时，可能挤掉真正有用的数据并拖慢搜索。[Elastic 预加载说明](https://www.elastic.co/docs/reference/elasticsearch/index-settings/preloading-data-into-file-system-cache)

对 MemWeft 建议分两步：

1. **先预热已有数据库页。** 暴露可配置的 SQLite 页缓存预算，并在启动或 Agent 任务开始前，对明确绑定的热点池执行少量代表性读取。设置预热读取量、时间、并发上限，允许取消和后台执行。优先读词项上界、索引入口及近期常用事实，避免把所有 JSON 正文复制进应用堆。
2. **再评估独立的内存索引/对象缓存。** 只有在页缓存与算法优化后仍有明显收益时引入。缓存键要包含 tenant、user、Agent/共享池及数据版本；多进程写入、遗忘、共享池修订与权限变更必须使旧项失效。仅用 TTL 不能满足“遗忘成功后不再返回旧记忆”的语义。

SQLite 的 `cache_size` 控制连接上的数据库页缓存建议上限，并不立即分配这些内存；配置要乘上连接池和进程数量，不能误把每连接预算当成整个服务预算。[SQLite cache_size](https://www.sqlite.org/pragma.html#pragma_cache_size)

`mmap` 是另一个独立的可测选项。SQLite 可以通过映射减少部分复制，但官方明确指出并非所有工作负载都会变快；还存在平台和编译上限。映射地址空间不等于主动预热，更不保证所有映射页常驻内存。应读取生效值、单独测试，不默认映射全部数据库。[SQLite mmap](https://www.sqlite.org/mmap.html)

现有 SQL **语句缓存**只复用已编译程序；它不是查询结果缓存，也不是上述数据预加载功能。操作系统缓存本来就在工作，预热的主要价值是提前承担冷读成本，改善启动、切换热点之后的延迟。

## 千万、亿级应如何扩展

下面是优先级建议，不是“到某个条数就必须换后端”的硬阈值：

| 情况 | 优先处理 |
|---|---|
| 热点工作集可放进一台机器内存 | 作用域索引、精确剪枝、内存预算、热点预热、压缩 |
| 总量很大，但每次只查少量用户/池 | 按 tenant/user/pool 路由，减少查询涉及的分片，给热点独立配额 |
| 单个大池也很大 | 可跳过的数据块、压缩倒排列表、分片内检索与正确的全局 Top-K |
| 高并发或跨机器扩展 | 副本、读写职责、负载治理、版本一致性与故障恢复 |
| 网络搬运已经成为主要耗时 | 才评估 RDMA 或其他传输优化 |

Elastic 的 routing 能把指定路由值的查询限定到对应分片；它也提醒访问过多分片会增加 CPU 和内存开销。这里借鉴的是缩小搜索范围的原则，不是要求 MemWeft 立即依赖 Elasticsearch。[Elastic 查询路由](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-shard-routing)

路由不能代替权限检查。私有池可以按 tenant/user/Agent 定位，共享池按 tenant/user/pool 定位；具体分片粒度需结合热点与池大小确定。混合查询还必须保留私有优先、read_order 和严格冲突语义。不能只从每个分片取少量结果再简单去重，否则可能恢复被高优先级池遮蔽的旧值；需要跨池资格检查或能证明完整性的增量取回。

针对两种规模，建议采用两层定位：先解析逻辑作用域与绑定，再定位该池包含的物理分片。一个逻辑池可覆盖多个分片，不能硬编码为一个租户或一个池永远对应一个分片。尽量让同名 key 的覆盖关系在相同分片内解析，不能对齐时增加跨池资格校验。迁移、拆分、合并和重试须保留唯一记录、修订号与删除语义。

Agent 侧继续表达独立池、共享池、访问权限和冲突策略；物理分片、热点预热与迁移属于存储层配置。内存预算同时设置节点上限和租户/池配额，共享池缓存可在同权限域内复用，私有缓存仍按 Agent 隔离。对热点大租户和大池单独验证倾斜、限流及故障恢复，避免总吞吐掩盖小租户的尾延迟。

如果以后把权威事实和搜索索引拆开，提交可见性、删除墓碑、修订号校验、索引落后时的读取策略都需要显式设计。检索加速不能以返回已经遗忘的数据为代价。

## RDMA 的位置

RDMA 允许支持它的设备在不同主机的内存之间传输数据，减少传统网络路径中的复制和部分 CPU/操作系统开销。它需要连接、内存区域与访问权限等应用适配。[NVIDIA RDMA 编程指南](https://networking-docs.nvidia.com/doca/archive/3-5-0/rdma-aware-networks-programming-guide)

因此本项目的判断是：

- 单机 SQLite 查询没有远程传输路径，RDMA 无法消除本地评分和排序工作。
- 多机时可以评估用 RDMA 读取远端不可变索引块或连接远程存储；先用测量确认网络耗时占比，再决定复杂度是否值得。
- 传输层不会自动提供数据库事务、持久化、分片路由、逻辑权限、缓存失效或故障恢复。仍需由存储/索引服务保证这些语义。
- 不把当前 SQLite 文件直接放进“远程共享内存”就当成完成了分布式改造。本轮未配置或验证 RDMA 硬件，也未实施该后端。

## 下一阶段验收

异步流水线作为后续执行架构纳入设计：前台检索与有界加载衔接，后台处理预热、维护和版本受控的压缩。已实现的可选后台 checkpoint 与仍待实现的部分见[异步流水线设计](async_pipeline.md)。

建议先做可配置页缓存和热点预热实验，保留关闭选项，分别比较冷启动、预热后、工作集超过预算三种情况。记录 p50/p95/p99、实际物理读取/缺页、CPU、进程和系统缓存占用、预热时长、写入长尾及更新后可见性。不要在开发机器上全局清理系统缓存来伪造冷启动；采用隔离测试环境或明确记录缓存控制方式。

之后分别扩大“多租户总量”和“单池规模”，验证热点倾斜、持续并发、删除和跨池覆盖。RDMA 的验收应另设网络传输占比、带宽、尾延迟和故障恢复指标，不能只拿微基准的远程内存延迟来推断完整记忆查询速度。
